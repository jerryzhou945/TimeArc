## Data Flow

```text
Raw service record
  -> parse into UsageStatManager::UsageRecord
  -> resolve adapter from app identifiers, process names, and browser title hints
  -> keep original grouping/display fields
  -> attach adapter metadata fields
  -> QML uses adapter fields first and falls back to original fields
```

No schema migration was added. This is intentional for the first adapter foundation because the existing automatic usage flow is still JSONL/current-file driven, and adapter metadata can be derived during read/aggregation.

## Database Compatibility

No database table or column was changed.

Old data remains compatible because:

- Existing raw fields are not removed.
- Existing `site_catalog` fallback logic remains available for older site grouping.
- Adapter failure falls back to old app/site classification and display logic.
- Unknown websites and unknown desktop apps get generic metadata.

Future work can persist normalized adapter metadata if query performance or historical consistency requires it.

## Privacy

This implementation does not add:

- Screen recording
- Screenshots
- Webpage body capture
- Input field capture
- Chat content reading
- Private content upload
- Default IP-based recognition

The adapter map intentionally does not serialize full URLs.

## Known Limits

- The service does not yet provide browser URL/domain fields for every foreground browser record, so website adapters currently rely on URL where available and title hints where only window titles exist.
- High-resolution website icon discovery is not automated yet. Known websites should use repo-local icons or future browser-provided favicon metadata.
- Adapter metadata is derived at read/aggregation time and is not persisted into the usage database.
- The app registry is intentionally small and high-frequency first.
