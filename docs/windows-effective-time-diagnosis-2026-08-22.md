# Windows 有效使用时长诊断与修复方案

## 结论

当前 Windows 采集不是单纯的“前台窗口停留时长”，而是把前台输入、音频输出和前台应用的自主进程活动组合起来判断有效使用。现有判断方向基本正确，用户看到 B 站和 Codex 增长迟缓的主要原因是：Windows 只在应用、标题或音频状态结束时写入完整会话，没有像 macOS 一样定期 checkpoint。长时间持续的视频、语音或命令仍停留在服务内存中，统计页刷新时读不到。

另有一个独立的统计口径错误：服务已经为前台会话保存 `active_sec`，但 `UsageStatManager` 当前读取的是 `duration_sec`。因此已写盘的前台记录仍可能把空闲墙钟时间算入 UI。该问题必须和实时 checkpoint 一起修复，否则“刷新更及时”仍不等于“有效时长准确”。

## 当前各类软件如何计时

| 场景 | Windows 当前信号 | 何时继续计时 | 何时停止或暂停 | 当前缺口 |
|---|---|---|---|---|
| 普通前台软件 | 活动窗口 + 键鼠空闲时间 | 用户仍有输入；或刚发生过可证明的自主活动 | 超过空闲阈值后暂停 active 累计；切换应用时结束会话 | UI 读取 `duration_sec`，可能重新把空闲时间算回去 |
| B 站等网页视频 | 浏览器前台身份 + WASAPI 音频峰值；窗口标题用于拆分站点 | 有输入、正在输出可检测音频，或处于 90 秒活动租约内 | 音频消失且无输入/自主活动后暂停；切标题/应用才写盘 | 持续播放时不 checkpoint，统计页看起来几乎不涨；静音视频也缺少可靠播放态 |
| 网易云音乐 | 独立 WASAPI 音频会话，不受键鼠 idle 影响 | 音频会话 Active、未静音、音量有效且有实际输出峰值 | 音频会话消失、静音或无输出峰值时结束 | 歌曲/标题变化常使上一段及时落盘，所以体感比网页视频准确 |
| Discord 语音 | 当前仍是 WASAPI 音频峰值，不是语音频道成员状态 | Discord 正产生可检测输出音频；前台操作也按普通前台计时 | 无音频峰值时媒体段会结束；若仍在前台操作则前台段继续 | 安静频道可能被切成很多短段，不能保证“只要在频道就连续计时” |
| Codex 自主运行 | 前台 Codex/ChatGPT 包进程树的 CPU 与 I/O 增量 | 每次检测到有效 CPU/I/O 后续租 90 秒；音频也可续租 | 90 秒内没有新活动且用户也 idle 后暂停 | 进程识别已覆盖包内同级 `codex.exe`，但开放会话不 checkpoint，UI 仍显得不增长；极低资源等待任务可能超过租约 |
| macOS 视频/音频 | CoreAudio 运行输出 + IOKit sleep assertion | 音频输出或视频类防休眠 assertion 存在 | assertion/输出结束 | 已按 `maxSessionSec` 定期 checkpoint，实时性优于 Windows |
| 手动项目/番茄钟 | UI 计时器与手动项目仓库 | 用户明确启动 | 用户暂停/结束 | 与自动应用采集分开，不应互相替代 |

前台与音频同时存在时，统计层会按应用合并重叠区间，避免同一秒因为“前台 + 音频”重复计算。

## Discord 是否会在退出频道后停止

按现有实现，Discord 退出频道并且不再产生音频后，媒体会话通常会在下一次成功轮询时结束；如果 Discord 此时仍是前台且用户正在操作，仍会按普通前台使用继续计时，这是合理的。

但现状不能严格表达产品要求，因为它检测的是“有无可听音频峰值”，而不是“是否仍连接语音频道”。安静频道可能中断，系统提示音也可能短暂触发。目标逻辑应改为：

1. 对 Discord、Teams、Zoom 等通信类软件检测活跃的 communications render/capture session。
2. 只要通信会话存在，就把“在语音频道/通话中”视为有效使用，不要求持续说话或播放声音。
3. 通信会话消失后立即结束该媒体段；仅仅进程仍在后台不能继续计时。
4. 前台键鼠使用仍作为另一条独立证据，退出频道后用户继续浏览 Discord 时仍可正常记录。

## 修复顺序

### C1：实时落盘已修复；有效时长读口径仍待修复

- Windows 测试版已采用固定 60 秒 checkpoint；后续再把周期接入 v1 的 `tracking.sampling.max_session_sec` 高级配置。
- 前台和音频开放会话到达 checkpoint 时，写入一段后从同一逻辑身份继续，不制造空洞，也不重复秒数；本机实测得到一条恰好 60 秒的开放前台记录。
- 浏览器媒体在与前台窗口匹配时优先保留浏览器标题，减少 B 站视频标题被错误归到通用 Chrome 的情况；原生音乐仍优先使用 GSMTC 歌曲标题。
- `UsageStatManager` 不再把前台 `duration_sec` 当有效使用时间。数据模型需要同时保留墙钟区间和 active 值，并用测试固定 idle、跨 checkpoint、前台/音频重叠的计算口径。
- 统计页刷新后应能读到最近一个 checkpoint，页面标明“数据更新于 …”，避免用户把未落盘误认为未记录。

### C2：增加通信会话存在检测

- 在 Windows 音频适配层增加 communications render/capture session 观察值。
- 通信类应用使用“通话会话存在”策略；音乐和视频仍使用实际输出/系统播放态，不能把所有 Active 音频 session 都当有效播放。
- 增加 Discord 三组回归：频道内静默继续、退出频道停止、退出后仍前台操作只计普通前台段。

### C3：加强网页视频和 Codex 的自主活动证据

- B 站优先组合 Global System Media Transport Controls 的 Playing/Paused 状态与音频输出；静音视频只有 Playing 时才续租，暂停页不续租。
- Codex 保留 CPU/I/O 增量 + 90 秒租约，不使用“进程存在即计时”。增加长命令、低 CPU 等待、命令结束后超时停止三类测试。
- 把租约状态、最后活动原因和开放会话 checkpoint 年龄写入诊断状态，不写入用户统计数据。

### C4：跨平台与发布前验收

- 用同一组脚本场景在 Windows/macOS 验证：普通 idle、视频播放/暂停、音乐播放/暂停、Discord 入会/退会、Codex 长命令、前台+音频重叠。
- 允许采样误差不超过一个轮询周期；checkpoint 分段后总时长必须与单段基准一致。
- 异常退出后最多丢失一个 checkpoint 周期，重启后不得重复累计。

## 本轮边界

统计页迁移仍属于 Track B。随后独立 Track C 已完成 Windows 60 秒开放会话 checkpoint 和浏览器前台标题优先；没有修改 SQLite 契约，也没有修改 Discord 音频判定。`active_sec` UI 读口径、通信会话存在检测及更完整的播放态仍按 C1 → C2 → C3 继续处理。
