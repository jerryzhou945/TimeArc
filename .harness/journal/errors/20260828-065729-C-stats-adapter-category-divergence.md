## 1. What happened

Ring/library/ranking classify via AppVisual.modelCategory() (adapterCategory first) while categorySums/rebuildRingLegend/buildCategoryDistribution read raw .category. applyRuleMetadata writes adapterCategory=rule->category after aggregateSoftware has already downgraded game->other for m_gameClassify=false, so with game detection off the ring draws a 'game' arc whose legend seconds resolve to 0m.

## 3. Root cause

- Immediate cause: `category` and `adapterCategory` are different things wearing the same name. `category` is what aggregateSoftware() resolved -- a duration-weighted per-record vote with the read filters applied -- while `adapterCategory` is raw rule metadata that no filter touches, and the aggregator deliberately lets the vote beat the rule. AppVisual.modelCategory() reads them in the opposite order, so the ring (via ringRawCategory) classified by rule while the legend, colour map and share donut classified by vote. With game detection off, C++ rewrote category to "other" but left adapterCategory as "game", so the ring drew a game arc whose legend read 0m.
- Underlying cause: Two classifiers on one page, plus a read-layer filter applied to only one of the two fields it should cover.
- Why the harness/checklists did not prevent it: Nothing named which of the two fields is authoritative; both are populated on every row, so either one 'works' until the two disagree.

## 4. Fix

- Files changed: src/services/usage_stat_manager.cpp, qml/desktop/pages/StatsViewModel.js, qml/desktop/pages/DesktopStatsPage.qml, tests/stats_view_model_test.js
- Short description: applyRuleMetadata() now applies the game-detection downgrade to adapterCategory too, so a row can no longer leave C++ carrying two contradictory categories. StatsViewModel.ringRawCategory() and the new DesktopStatsPage.rowCategory() both read `category` first and keep `adapterCategory` only as the fallback for segment rows, which carry nothing else; every classifier call site on the page now routes through rowCategory(). buildCategoryDistribution() also stopped falling back to a capitalised "Other" that categoryLabel() could not resolve. Two assertions added to tests/stats_view_model_test.js pin the precedence and the fallback id.
- Commit: pending commit

## 5. Prevention

Rule upgrade: rules/03-data-contract.md should state that `category` is the resolved, read-filtered value and `adapterCategory` is un-filtered rule metadata, and that UI must prefer the former. AppVisual.modelCategory() still uses the opposite order for Home and Memory Lake and should be revisited in its own session.
