## 1. What happened

allApps() deliberately includes hidden apps (for the settings un-hide list) while every other read path filters m_hiddenKeys. dayMetrics() uses lifetimeApps[0] for 'Longest overall' so a user-hidden app can be named there, and 'Active apps this period' prints lifetimeApps.length while the App Library card below counts hidden-filtered rows.

## 3. Root cause

- Immediate cause: allApps() deliberately returns hidden rows so Settings can offer to un-hide them, and marks them with hidden:true. Every other read path drops them at source via m_hiddenKeys. The stats page consumed allApps() raw, so dayMetrics() took lifetimeApps[0] (possibly a hidden app) as 'Longest overall' and printed lifetimeApps.length as the 'All' count.
- Underlying cause: One producer serves two audiences with opposite needs. Only the lifetime *total* was written to skip hidden rows, so the filtering existed but stopped one line short.
- Why the harness/checklists did not prevent it: The read-filter contract is enforced in C++ for the aggregate paths but is the caller's responsibility for allApps(), and nothing states that.

## 4. Fix

- Files changed: qml/desktop/pages/DesktopStatsPage.qml
- Short description: rebuild() now builds a visibleLifetime list in the same pass that sums lifetimeTotal, and that list feeds vmLifetimeApps and dayMetrics(). buildAppLibrary() already skipped hidden rows, so its output is unchanged.
- Commit: pending commit

## 5. Prevention

Rule upgrade: rules/03-data-contract.md should name allApps() as the one read API that returns hidden rows, and state that every consumer other than the settings list must filter hidden itself.
