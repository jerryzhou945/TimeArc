## 1. What happened

DesktopStatsPage has no onNightModeChanged handler. categoryColorMap is only rebuilt inside the gen/range/offset-guarded rebuild(), and ringCanvas only repaints on arcs/activeId/size, so toggling night mode from the macOS menu bar while on Stats leaves the ring track, ticks and every category swatch in the previous theme's palette. DesktopHomePage and DesktopCalenderPage both handle this.

## 3. Root cause

- Immediate cause: rebuild() skips its work unless the data generation, range or period offset changed, and categoryColorMap is only produced inside rebuild(). A night-mode toggle changes none of the three, so AppVisual.buildCategoryColors() was never re-run for the new theme, and the ring Canvas -- which tracks nothing it paints with -- was never asked to repaint.
- Underlying cause: The guard was added to stop a 5s idle tick from re-aggregating the whole window. It correctly treats 'no new data' as 'nothing to do', but theme is a second input to the derived values that the guard does not model.
- Why the harness/checklists did not prevent it: No checklist item asks whether a new memoised/guarded value depends on the theme. DesktopHomePage and DesktopCalenderPage each solved this separately, so the pattern existed but was never written down.

## 4. Fix

- Files changed: qml/desktop/pages/DesktopStatsPage.qml
- Short description: Added onNightModeChanged: { _builtGen = -1; rebuild() }, matching the existing onLanguageModeChanged treatment of the same guard.
- Commit: pending commit

## 5. Prevention

Rule upgrade: rules/04-ui-conventions.md should state that any value derived from nightMode must be invalidated on nightMode, and that a Canvas needs an explicit requestPaint() because it does not track the tokens it draws with. Three pages have now hit this independently.
