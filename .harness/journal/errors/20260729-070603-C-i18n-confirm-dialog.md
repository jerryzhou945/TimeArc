## 1. What happened

Settings confirm card rendered titleText/msgText without tr(), so
English/Japanese mode showed a mixed dialog: tr()-routed buttons read 'Cancel'
next to the raw Chinese title, body and '打开文件夹' label. Dictionary entries
were also missing for the 导入导出 cards, and dynamic bodies were concatenated
in JS so they could never be dictionary keys.

## 2. Evidence

User screenshot, `language_mode = en` (confirmed in the GUI settings table):
the "Back Up Database" confirmation reads

```
数据库已备份
已保存到：
/Users/jz2025/Downloads/timearc-backup-20260729-042720.db
            [ Cancel ]  [ 打开文件夹 ]
```

"Cancel" is English because `"取消"` has an `en` entry and GhostBtn routes its
label through `tr()`. Everything else in the same card is Chinese. The card
behind it shows the same split: `数据库备份与恢复` → "Database Backup &
Restore" (entry exists) but `服务数据库目录` and `设置目录…` stay Chinese
(no entry), next to an English "Restore Default Location".

## 3. Root cause

- Immediate cause: three independent holes lined up in one card.
  1. `confirmCard` bound `text: confirmCard.titleText` / `msgText` directly —
     no `tr()` at the render site, so no dictionary could ever apply.
  2. `en`/`ja` had no entries for the confirm-dialog strings, nor for
     `服务数据库目录` / its cardDesc / `设置目录…` in the 导入导出 section.
     `ja` had **no** entry for any string in that section.
  3. Message bodies were built by concatenation at runtime
     (`"已保存到：\n" + p`, backup-preview counts, relocate path). A string
     assembled at runtime can never match a source-keyed dictionary entry.
- Underlying cause: the dictionary is keyed by Chinese source text, so
  "does this string translate?" depends on a lookup that is invisible at the
  call site. A literal that renders fine in zh looks identical to one that has
  an entry. Nothing failed loudly; the card just degraded per-string.
  Same keying also silently collides: the confirm label `"设置"` would have
  rendered as "Settings" (the navigation entry), not "Set".
- Why the harness/checklists did not prevent it: no rule or test covered i18n
  coverage. `rules/04-ui-conventions.md` does not mention the dictionary, and
  no static test asserted that user-visible literals resolve in every language.

## 4. Fix

- Files changed:
  - `qml/desktop/pages/DesktopProfilePage.qml` — `tr()` at the confirm-card
    title/message render sites; `sentence()` for the three runtime-built
    bodies; `tr()` on the FileDialog `nameFilters`; confirm label
    `"设置"` → `"设置此目录"` to clear the navigation collision.
  - `qml/desktop/components/I18n.js` — `en` and `ja` entries for the
    confirm-dialog strings, the 导入导出 cards and the file-dialog filters;
    `savedToPath` / `backupPreview` / `relocateSuccess` sentence templates in
    both `sentencesEn` and `sentencesJa`.
  - `tests/i18n_settings_dialog_static_test.py` — new.
- Short description: translate the whole settings confirm card and the
  backup / service-database-location cards in zh, en and ja.
- Commit: (uncommitted at time of writing)

## 5. Prevention

`tests/i18n_settings_dialog_static_test.py` pins all three holes: it asserts
the render sites call `tr()`, that every literal handed to `askConfirm()` /
`showSavedAt()` and every 导入导出 card string resolves in both `en` and `ja`,
that the three dynamic bodies route through `sentence()` with templates in
both tables, and that no confirm label reuses `"设置"`. Its literal scan fails
loudly if the parser drifts, so a new dialog cannot pass by going undetected.

Not covered by the test, and worth a later track-A pass: `ja` coverage is
partial across the rest of the app (183 entries vs 521 in `en`), so untranslated
Japanese silently reads as English via the ja → en fallback. The same
concatenation bug also remains in the toast path
(`"无效备份：" + info.error`, `"迁移失败：" + res.error`), where the error text
originates in C++ and is not translated at all.
