## 1. What happened

Stats period chip renders literal '2026Year8Month' / '2026Year' in zh+ja: commit b7abaab replaced the CJK 年/月 inside a JS concatenation that was already the non-English branch of isEnglish(). Leaks into periodText, aggregateContextText() and exported JSON 'period'.

## 3. Root cause

- Immediate cause: Commit b7abaab ("Multilingual Support") ran a mechanical CJK->English pass over the source tree and rewrote `year + "年" + month + "月"` to `year + "Year" + month + "Month"`. That concatenation was the **non-English** branch of an isEnglish() ternary, so the replacement inverted its meaning instead of translating it.
- Underlying cause: The period label was hand-assembled at the call site even though I18n.yearMonth() already existed for exactly this string, so there was a second copy to get wrong.
- Why the harness/checklists did not prevent it: i18n_source_coverage_static_test only resolves string *literals* passed to tr()/I18n.t(). A label built by runtime concatenation is invisible to it, in any language.

## 4. Fix

- Files changed: qml/desktop/pages/DesktopStatsPage.qml, qml/shared/I18n.js
- Short description: periodWindow() now calls I18n.yearMonth() for the month label and a new I18n.yearLabel() for the year label, deleting both hand-built branches.
- Commit: pending commit

## 5. Prevention

Harness upgrade: extend i18n_source_coverage_static_test to flag string concatenation of a bare English calendar word ("Year"/"Month"/"Day") onto a number in qml/**, which is the shape this regression took and which no current pass can see.
